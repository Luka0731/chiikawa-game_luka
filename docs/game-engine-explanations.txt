-*- perspective and orthographic projections
* Perspective Projection: Objects farther away appear smaller. It creates a realistic 3D effect.
* Orthographic Projection: Objects keep the same size regardless of distance. There is no perspective distortion and is
  often used in 2D or isometric games.
-*- clipping plate
Defines near and far limits of camera view; anything outside gets clipped (not rendered).

|--- batch rendering ---|
Instead of sending 1000 draw calls for 1000 sprites, you combine them into ONE draw call with all the vertex data
together. Much faster! Like mailing 1000 letters in one box instead of 1000 separate trips to the post office.

|--- asset pool ---|
A central storage that keeps loaded assets (textures, shaders) so you don't load the same file twice. If 50 enemies use
the same texture, you load it once and share it throughout the game.

* Texture -> The texture is pure data made for the GPU. It is very much on the OpenGL side and knows nothing about game
             logic.
* Sprite -> Sprite is like a window into the texture. It defines wich part of the texture is shown and how big it
            should be.
* Spritesheet -> Spritesheet is more of a helper class. It splits a texture into multiple sprites easily. Especially
                 handy if u will do animations, cause they require allot of similar sprites.
* SpriteRenderer -> SpriteRenderer is a component. Made, so that a object then can have visual existence. It has a
                    sprite and other attributes, like tint color and other game logic.
* RendereBatch -> It reads from the SpritRenderer and sends the data to the GPU. Also including batch rendering logic
                  wich i explained a bit more at the top.
Doing this whole system like this has many advantages. To count some of these as examples. First with separating
textures and sprites, you can have a few textures, but allot of sprites that use different parts of these textures. In
the end it saves allot of memory. Also it is more efficient because of systems like Batch Rendering and Dirty Flag
Optimization. It is also a good split between responsibilities of the classes, making the code cleaner.

|--- traditional serialization and serialization with reflection ---|
Serialization is when you turn objects into a savable format. In this engine we save the game in a file called
level.txt as a json. It is not encrypted, but will be in the future. Deserialization is the opposite.
-*- traditional serialization
There you used to wright code on which attributes it should save and to name it -> "  json.put("name", this.name); "
It is hard to maintain and makes a lot of boilerplate code.
-*- serialization with reflection
This is the modern way. Reflection basically means that it decides during runtime what attributes it will serialize. In
this engine the library GSOn is used for this, that does that. U basically only have to implement a interface into the
classes that you want to serialize/deserialize. I have also made TypeAdapter Classes for GameObject and Component, to
handle polymorphic serialization for them.

|--- framebuffers  ---|
So what normally happens in this game engine, is that there is the game (sprites, physics, objects, etc.) and it
directly draws it to the screen. But what you can also do is save that whole game in a texture(called a framebuffer)
and only then draw it to the screen. The advantages of this framebuffer method is, that you can ofc put a cool filter
over the texture. You can also adjust the size, making it maybe only a forth of the screen size.

|--- rbo  ---|
RBO (Render Buffer Object) is used when you need to store render data (like depth or stencil info) but don't need to
read it back as a texture. It's faster than a texture because OpenGL can optimize it - you can only write to it, not
sample from it. In this project, it stores depth information for the framebuffer.
